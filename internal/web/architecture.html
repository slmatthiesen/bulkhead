What a message is because everything below depends on it

A message is a run id and a delivery count. That is the whole thing — the work itself never travels. The steps, their inputs, their outputs and the answer all live in Postgres from the moment the run is created, and the message is a pointer saying somebody should be working on this one.

That is why losing a worker loses nothing. There is no payload in flight to drop, and no state in a process to reconstruct — only a claim that stopped being renewed.

whenwhat happenswhere the work is
You ask a question POST /runs writes the run and the question to Postgres, then enqueues its id. Two writes, one transaction's worth of intent. Postgres
A worker claims it The row is hidden for the lease duration and deliveries increments. Nothing is copied anywhere. Postgres
The run executes Each step is written before it runs and updated after. The worker holds no durable state of its own. Postgres
It finishes The message is deleted. Until that delete, it comes back. Postgres

How a stopped run gets picked back up

Nothing here polls for stuck work or reconciles state on a timer. A run that stops is a message whose lease nobody renewed, and that is the only condition anything has to detect.

what stoppedwhat picks it back upwho does it
One worker died
others still running		 It stops renewing the lease. Within the lease window the message becomes visible again and another worker claims it, replays the completed steps from the checkpoint store, and carries on from the step that was in flight. Nobody. Seconds, unattended.
Every worker died
the whole process is gone		 The message stays in the queue with an expired lease — visible, unclaimed, and waiting. Nothing is lost, because nothing was ever held in memory. When a process comes back it claims the message on its normal poll; recovery is not a startup routine, it is the same loop as always. Whatever restarts the process — ECS, Kubernetes, or the Restart button in this demo. Then it is automatic again.
The run itself keeps failing
a poison message		 Each delivery increments a counter, visible in the log as deliveries=N. That number is the signal to stop retrying and route the message aside for a human rather than loop on it forever. Not built yet — dead-letter queue, Milestone 6.

Why duplicates are assumed rather than prevented

Exactly-once delivery is not available to anything that talks over a network, so nothing here claims it. The queue delivers at least once, and a second delivery is made harmless three ways: a step is written down before it runs, a step that already completed is replayed from its checkpoint instead of re-executed, and the one step with an effect in the world carries an idempotency key the receiving system can recognise. Kill the control plane mid-send and the vendor still receives exactly one purchase order.
